# Payload CMS experience: plugin and built-in options

Researched 2026-11-04 against first-party Payload documentation, the npm registry and this checkout. **Status update, C41:** the user approved the three-phase implementation after this research. Core dashboard/branding, Lexical, drafts/history, protected preview, S3/R2 public media and SEO are implemented in the working tree. Other plugin suggestions remain proposals. Live R2 credentials were explicitly deferred; deployment/provider verification remain separate. See [the staff/operator guide](CMS_STAFF_GUIDE.md). The current roles and launch boundaries remain in [the MVP plan](MVP_PLAN.md).

## What would improve this CMS most

The strongest first step is a purposeful staff homepage, clearer editing screens and safe content preview. Installing a large plugin bundle would add navigation items without necessarily helping a nurse find today's work. Payload already provides the extension points for these first improvements.

Before the upgrade, repository inspection found Payload and its database/Next packages pinned to `3.92.0`, Next.js `16.4.3` and React `19.3.1`. The configuration has six collections and one global, the default collection-card dashboard, plain textareas for public prose, no media collection, no rich-text editor, no enabled content versions/drafts and no configured plugins. Care and payment records already have role-based access. These are source observations, not a browser assessment of the deployed CMS.

Recommended direction: a small, branded staff workspace with **new enquiries, today's appointments, training shortcuts, content editing and help**. Editors should see public-content tasks; care staff can see authorised operational tasks. Use the existing collection forms underneath it.

## Official packages worth considering

These are maintained in Payload's ecosystem. Each package below has an npm `3.92.0` release and declares an MIT license in its registry metadata. They do not require buying a separate plugin license; external storage, monitoring and delivery services can have their own charges. Runtime fit and permission behaviour still need testing.

| Package | Staff benefit | Fit and integration needed | Recommendation |
| --- | --- | --- | --- |
| **`@payloadcms/richtext-lexical`** | Familiar formatting, headings, lists, links and controlled reusable content blocks. | Official rich-text editor package rather than an ordinary `plugins` entry. Start with public service/course/resource prose. Current descriptions are strings rendered inside `<p>` in Astro; changing them to Lexical JSON needs a content migration, shared type changes and a renderer. Restrict formatting to the site's design. | Highest-value editor package |
| **`@payloadcms/storage-s3`** | A durable media library where nurses can upload approved public images and resource PDFs. | Requires an upload-enabled media collection, alt-text fields, file limits, storage credentials and Astro photo relationships. Supports S3-compatible services such as R2. On our Node host, use this adapter for R2, not the Workers-only `storage-r2` binding adapter. | Strong next step once uploads are approved |
| **`@payloadcms/plugin-seo`** | Editable page titles, descriptions, social-share images and metadata previews. | Adds metadata fields to selected public collections/globals. Astro must read and emit the fields. “Auto-generate” can use our deterministic defaults; it does not mean AI is required or automatic SEO success. Do not enable on private records. | Early content enhancement |
| **`@payloadcms/plugin-redirects`** | Manage old-to-new public URLs after changing a service/course slug. | Adds redirect records; Astro or the public routing layer must apply HTTP redirects. An installed CMS plugin alone does not redirect Astro visitors. Restrict destinations and editor access. | Add when URLs start changing |
| **`@payloadcms/plugin-import-export`** | Preview, import and export CSV/JSON through the admin UI. | Useful for a larger training catalogue and approved reporting. Start with public services/courses and admin-only operations. Export file collections need their own access rules; do not assume source-record permissions protect generated files. Large queued jobs need a runner and durable file storage. | Later, scoped to a real workflow |
| **`@payloadcms/plugin-search`** | A compact search collection synchronised from selected public documents. | Primarily a website-search building block, not an admin command palette or replacement dashboard. Astro still needs a search UI. Allowlist published public content and minimal fields; search copies must not include private enquiries/notes. | Later, once the public resource library grows |
| **`@payloadcms/plugin-form-builder`** | Staff can assemble reusable forms without a developer changing every field. | Adds form/submission management; Astro still needs a renderer/submission flow. Could suit event feedback or workshop surveys. It should not casually replace the existing validated care intake and its privacy/permission boundaries. Email notifications depend on real email configuration, currently disabled here. | Defer until staff need several distinct forms |
| **`@payloadcms/plugin-sentry`** | Developer-facing exception reporting connected to Sentry. | Helps maintenance rather than making the editor visually richer. This app already has safe runtime diagnostics; adding an external error service needs separate configuration and careful payload scrubbing. | Optional operations improvement |

Primary sources, accessed 2026-11-04: [Lexical](https://payloadcms.com/docs/rich-text/overview), [storage adapters and Node/R2 guidance](https://payloadcms.com/docs/upload/storage-adapters), [SEO](https://payloadcms.com/docs/plugins/seo), [Redirects](https://payloadcms.com/docs/plugins/redirects), [Import/Export](https://payloadcms.com/docs/plugins/import-export), [Search](https://payloadcms.com/docs/plugins/search), [Form Builder](https://payloadcms.com/docs/plugins/form-builder), [Sentry integration and required Next.js setup](https://payloadcms.com/docs/plugins/sentry). Benefits and prioritisation in the table are our recommendations; package capabilities come from those sources.

## Version and maintenance checks

The registry was queried read-only at exact version `3.92.0` for all eight packages above. Each declares `payload: 3.92.0` as a peer. Import/Export additionally declares `@payloadcms/ui: 3.92.0`; Lexical declares `@payloadcms/next: 3.92.0` and specific Faceless UI peers. Packages that declare React peers use `^19.0.1 || ^19.1.2 || ^19.2.1`; the installed React `19.3.1` falls inside those semver ranges. That is metadata compatibility, not an installation/build/browser result.

Use matching exact Payload package versions rather than adding `@latest` to this pinned application. Refresh package metadata and changelogs at implementation time, install only the selected package and review schema migrations before deployment. Public-content changes must preserve existing strings/photos/URLs and the service/course enquiry context.

## A practical order to improve it

1. **Make the start screen useful.** Use core widgets for work counts, appointments, shortcuts and brief help, with separate content-editor and care-team views. Add the organisation logo and modest brand colours. Improve field labels/help and default list columns. No plugin is necessary for this first batch.
2. **Make editing safer and more visual.** Add public-content history/drafts, an ordinary preview link and a restricted Lexical toolbar. Migrate existing content and render it in Astro. Prototype embedded Live Preview only after the basic preview works safely.
3. **Give nurses control of public assets and sharing.** Add a public media library with durable object storage, alt text and folders as needed, then SEO fields and frontend output. Retain the existing licensed photographs until staff deliberately replace them.
4. **Add tools when the workflow justifies them.** Trial CMDK for quicker navigation; consider the sidebar if native groups become crowded. Add Redirects for changed slugs, scoped exports for reporting, public search for a larger library and Form Builder for separate feedback/event forms. Evaluate audit or booking suites as separate workflow decisions. Extra menus alone do not solve the current dashboard problem.

This sequence was subsequently approved as C41; other plugin candidates remain proposals. The recommended first batch covers the staff homepage, branding, clearer list/form layouts and quick links; richer editing and durable uploads follow as separately testable changes.

## Hosting and data boundaries

Render Free uses an ephemeral filesystem and sleeps when idle. Uploaded media and generated export files cannot rely on its local disk for durability; long background import/export jobs should not be promised without a reliable runner. Object-storage pricing and provider selection remain open. See [Render Free limitations](https://render.com/docs/free), accessed 2026-11-04, and the [existing deployment guide](RENDER_DEPLOYMENT.md).

The new dashboard must preserve the existing `admin`, `care-team` and `editor` boundaries. Queries, exports, search copies, previews and media URLs are all additional data surfaces; a hidden menu alone does not protect them. Keep client details out of public search/SEO/media and use only synthetic records for plugin evaluation. Version history is useful for public copy recovery; it is not a complete private-record audit or retention policy.

## What was and was not verified

Verified: current CMS configuration and frontend rendering/framing boundaries by source inspection; official and maintainer documentation; presence, license declarations and peer ranges of the listed npm releases; installed dashboard-widget types. Community versions are registry observations, not endorsements of their security or completeness.
